\section{Engineering Implications and Limits}
Resumable analysis trades additional state and publication delay for control
over when engine-thread work executes. It is useful only if reduced bursts
justify the total CPU cost and spectrum age in the intended host. An optimized
batch transform may already fit the callback budget; a worker can move analysis
off the engine thread, and a sliding formulation may suit a small set of
frequently updated bins. Comparisons must match input windows, output
processing, and cadence, and report publication delay alongside engine cost.

The quota bounds scheduled work counts, not execution time. Window preparation,
butterflies, and output mapping have unequal costs, and the fixed weights do
not eliminate those differences. The historical measurements do not evaluate
the production weighting policy. Observed timing maxima also do not establish
a safe worst-case bound~\cite{wilhelm2008}. The scheduler finishes each quota
before advancing its logical hop; a late host call therefore preserves that
logical sequence but does not rescue an audio deadline.

Device callbacks accumulate many sample calls and other engine work, so host
load and coincident analyzer phases matter. Publication is also only one stage
of visualization latency~\cite{prusa2016}: exact-hop output does not guarantee
equally spaced screen updates or bound display age. Missed audio deadlines,
missed requested publications, and snapshots superseded by a slow display are
distinct outcomes. The archived campaigns do not measure this end-to-end path.

The evidence is limited to one host and compiler, few repetitions, same-session
resampling, and no optimized-library baseline or end-to-end Rack workload.
Independent direct-transform checks cover only small sizes; large-size checks
establish schedule equivalence. The timing campaigns do not test non-power-of-two
lengths, inverse applications, concurrent display consumption, or calibration
of every window and display setting. Production regression tests are separate
from timing evidence. Appendix~\ref{app:evaluation-agenda} retains the detailed
proposals for matched backends, overlap reuse, numerical error, host contention,
statistical replication, and work granularity; these remain proposed comparisons.
