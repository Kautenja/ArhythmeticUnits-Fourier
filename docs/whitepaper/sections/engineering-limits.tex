\section{Discussion and Limitations}
The useful design choice is how much result delay to exchange for a smaller
processing burst. For a visualizer whose native batch analysis comfortably
fits the host budget, the added state and overhead of a resumable transform
may be unnecessary. When several transforms coincide or one transform
occupies a large share of the block, distribution can leave substantially more
headroom. The one-thread Rack result demonstrates that regime, while the
native hybrid results show that scheduling the surrounding stages may already
be sufficient.

The FFT kernel and the scheduling policy should therefore be chosen together.
An efficient native kernel reduces total work, but an indivisible call sets
a lower limit on how finely that work can be spread. A resumable kernel gives
more control over placement, but repeated indexing, dispatch, and smaller
memory operations can cost more. The measured four-channel example shows that
a sufficiently efficient native hybrid can beat a fully distributed kernel
even on peak time. This is why operation-count bounds and timing measurements
answer different questions.

The delay also belongs in the design decision. A frame timestamp identifies
the analyzed signal, not when the user sees it. In the retained headless
consumer experiment at 60\,Hz, default Fourier snapshots have median
endpoint-age bounds of 38--40\,ms for production and the full-hop hybrid,
versus 8--10\,ms for native batch. That roughly 30\,ms difference matches
the schedule; it excludes repaint. Slower or stalled consumers skip some
published frames. No listening, interaction, or visual-response study was
performed, so acceptable display latency remains an application requirement.

The evidence has three main limits. First, both sessions were collected on
one machine, binary, and date, with residual operating-system activity. Their
ranges describe repeatability under those conditions, not portability or
rare-event probabilities. Second, the engine was driven by a synthetic release
schedule without a physical audio device or GUI rendering. Release misses
cannot be interpreted as audible dropouts. Third, the evaluation compares a
specific resumable radix-2 implementation with specific native adapters. It
does not test a background analysis worker, sliding-spectrum reuse, or native
sub-FFT leaves, and it does not establish an optimal granularity.

The implementation has corresponding boundaries. Credits are not equal-time
units, and their weights were tuned during earlier engineering on the same
machine. Lifecycle callbacks, UI work, other shared controls, and external
interruptions fall outside the per-sample accounting. Input retention and
mailbox ownership solve particular data-lifetime problems; they do not make
the entire plugin a hard real-time system. The result is a bounded schedule
for the ordinary analysis path, with measured rather than guaranteed
execution times.

These limits suggest a direct next experiment: compare batch, hybrid, and
fully distributed analysis under matched complete-module workloads on several
hosts and architectures, including demanding smoothing settings and actual
audio-device deadlines. Shorter completion intervals and native FFT leaves
could then be selected against explicit peak-cost and display-age targets.
The present evidence is sufficient to motivate that comparison without
assuming its outcome.
