\section{Experimental Method}
\label{sec:evaluation}
The evaluation asks two questions: does spreading a fixed implementation
reduce processing bursts, and how does that tradeoff compare with native
FFT-based analysis inside a real host engine? We use the retained study
collected on September 30, 2026: two separately prepared sessions on one Apple
M1 Pro laptop running macOS 26.6.2, with Apple Clang 21.0.0. The measured C++ uses the Rack build flags, including \code{-O3} and
\code{-funsafe-math-optimizations}; dependency identities and complete compile
commands are archived. Both sessions use the same executable and sources. Each planned configuration was
run in two fresh processes per session, giving four processes per comparison
row. The complete campaign contains 194 planned cells and 776 processes,
including scaling, numerical stress, and lifecycle cases beyond the selections
reported here.

\subsection{Comparisons and workloads}
The \emph{matched batch} and \emph{matched distributed} controls use the same
scalar implementation, storage, arithmetic, and frame endpoints. Batch spends
all credits in the endpoint call; distributed spends them according to
Equation~\eqref{eq:quota}. This isolates placement within the implementation.

The native controls use PFFFT, FFTW, or vDSP for the transform. Each provider
has a batch path and a \emph{hybrid}: the hybrid distributes input preparation
and output processing but executes the native FFT and any required reordering
as one indivisible call. Within each provider, the two paths share retained
input, windowing, magnitude calculation, and smoothing. Native layouts are
used directly where possible. vDSP uses vectorized preparation and batched
four-channel transforms; FFTW uses reusable real plans, including batched
plans for four channels, with single-threaded \code{FFTW\_MEASURE} planning
and no imported wisdom. Plan creation occurs before measurement.

Controlled comparisons use 48\,kHz input, 64-sample blocks, a Hann window,
and no smoothing unless stated otherwise. The main scalar comparison uses
$N=4096$, $H=1024$. A four-channel comparison uses $N=16384$, $H=240$
and varies the hybrid's completion interval while keeping the hop fixed.
These calls feed a controlled output sink. They measure complete analysis,
but omit module input conditioning and display conversion.

Host comparisons run complete Fourier modules through Rack's
\code{stepBlock()} entry point, including worker synchronization. Native
controls replace the analysis inside the same module shell, retaining input
conditioning, display conversion, and publication. The reported host rows use
Fourier's defaults, one or four engine threads, and four or sixteen modules.
Aligned modules share frame endpoints; staggered modules start at different
phases. No background modules or display consumer are active in these rows.
The host is paced at the nominal block period; controlled analysis runs
continuously. Results from those different execution regimes are not treated
as interchangeable timings.

\subsection{Measurements and replication}
We measure the duration of each whole processing block. To keep sparse FFT
bursts visible, the primary statistic takes the longest block intersecting
each complete frame-to-frame hop, then reports the median of those maxima.
We call this the \emph{typical hop peak}. A block crossing a hop boundary
counts in both intervals. The same full-hop interval is used for immediate
and delayed publication. Thus a batch method is not favored merely because
it publishes sooner, and a rare frame boundary does not disappear beneath a
callback percentile.

Aggregate cost is the sum of instrumented block wall times divided by engine
samples, in ns/sample. It includes dispatch, timing overhead, and
interruptions; it is not an independently measured throughput or CPU
utilization figure. A \emph{compute-budget exceedance} occurs when a timed
block takes longer than $D/f_s$. A \emph{release miss} occurs when the paced
host finishes after its scheduled deadline, including wake lateness and any
backlog. Neither statistic is an audio-device underrun count.

Every process warms up for 16 nominal hops. Setup, correctness replay, and
result serialization are outside the timed blocks. Within each session we
average the two process costs and take the median of their hop-peak
summaries; the published result weights the two sessions equally. Bracketed
ranges show the two session summaries, not confidence intervals. We retain
all processes and slow observations. With two sessions on one machine,
treating individual blocks as independent replicates would overstate the
evidence~\cite{kalibera2013}.

The operator prepared the machine offline, on AC power with Low Power Mode
disabled, and closed unnecessary applications. Pre/post snapshots still show
macOS service activity. No affinity, frequency lock, or real-time thread
priority was applied. Timings therefore describe this host and build under
the recorded conditions rather than worst-case execution time.

\subsection{Numerical verification}
Every measured path has a separate output replay checked against a direct
DFT at small lengths and a separately structured double-precision FFT at
larger lengths. Complete-module references also model input conditioning and
display conversion. Relative vector $\ell_2$ and $\ell_\infty$ errors must
stay within $3\times10^{-4}$ for float or $10^{-10}$ for double; a zero
reference requires zero output. Long module decays have a separately flagged
region affected by flush-to-zero and display mapping, checked against an
explicit absolute floor and excluded from relative-accuracy claims.

The source archive, compact evidence, process summaries, and deterministic
table generator are retained with the paper. Its build reads those results;
it does not run a new benchmark. The original raw sessions remain local,
so the repository is not presented as a public raw-data deposit.
